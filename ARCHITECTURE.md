# ARCHITECTURE

A map of the code as it stands. `lib/` is Elixir; `native/xqlitenif/src/`
is a Rust crate compiled into a NIF library by Rustler, talking to a
statically linked SQLite through rusqlite. `XqliteNIF` holds nothing but
101 raw NIF stub declarations (every body is `err()`, replaced at load
time by the native function); `Xqlite` wraps most of them with option
validation, result structs and telemetry.

## 1. Module map

Elixir paths are relative to `lib/`, Rust paths to
`native/xqlitenif/src/`.

- `xqlite.ex` — the high-level API: open/close, `query/4`, `execute/4`,
  `stream/4`, the prepared-statement calls, transactions and savepoints,
  the busy policy and observers, `register_progress_hook/3`,
  cancellation, backup/serialize, PRAGMA get/set, schema introspection,
  STRICT-table helpers. It has no wrapper for the update / WAL / commit /
  rollback / log hooks — those are called on `XqliteNIF` directly.
- `xqlite/xqlitenif.ex` — the 101 stubs plus `use RustlerPrecompiled`.
- `xqlite/result.ex`, `explain_analyze.ex` — result structs with
  `from_map/1`; `Result` also implements `Table.Reader`.
  `xqlite/stream_resource_callbacks.ex` and `stream_error.ex` hold the
  `Stream.resource/3` callbacks and the exception they raise;
  `xqlite/pragma.ex` and `pragma_spec.ex` hold 53 typed PRAGMAs with
  `get/4`, `put/4`, validation and per-schema targeting.
- `xqlite/type_extension.ex` and `type_extension/*.ex` — the
  `encode/1` / `decode/1` behaviour, the chain runners, and nine
  built-ins (`Date`, `DateTime`, `NaiveDateTime`, `Time`, `JSON`, `UUID`
  both ways; `Instant`, `Duration`, `Decimal` encode only).
- `xqlite/telemetry.ex`, `telemetry/bridge.ex`,
  `telemetry/open_telemetry.ex` — the compile-gated macros and
  `enabled?/0`, the GenServer re-emitting hook deliveries as
  `[:xqlite, :hook, :*]`, and a dependency-free map to OpenTelemetry
  attribute names.
- `xqlite/schema/*.ex` — the six structs the Rust side builds, plus
  `Types`; `mix/tasks/verify.ex` and `test_seq.ex` — the pre-commit gate
  (cargo runs with cwd set to the crate directory) and the test runner.
- `lib.rs` — atoms, module list, `rustler::init!`; `nif.rs` — all 101
  `#[rustler::nif]` functions, 95 of them `DirtyIo`; `connection.rs` —
  the `XqliteConn` resource (a `Mutex<Option<Connection>>`, the child
  registry, and every hook slot), `with_conn`, `with_conn_mut`,
  open/close, result encoding.
- `statement.rs`, `stream.rs`, `blob.rs` — the three raw-pointer
  resources (a shared `AtomicPtr` plus `with_live_*`),
  `take_and_finalize_raw`, `process_single_step`, the raw binders.
- `session.rs`, `cancel.rs` — `XqliteSession` with its
  leak-rather-than-dangle `close`, and `apply_changeset`, the conflict
  logic of `changeset_apply/3`; `XqliteCancelToken` with the RAII
  `ProgressHandlerGuard`.
- `hook_util.rs` — term helpers, the single-slot `AtomicPtr` lifecycle,
  the copy-on-write `HookList<T>`, `guard_ffi_callback`.
- `progress_dispatch.rs`, `busy_handler.rs`, `wal_hook.rs`,
  `update_hook.rs` and the authorizer below — the five raw C callbacks:
  progress ticks and cancel checks, the busy slot, the WAL fan-out plus
  emulated checkpoint, the update fan-out to a `HookList`.
- `commit_hook.rs`, `rollback_hook.rs`, `log_hook.rs` — master closures
  installed once, fanning out to a `HookList`; the log one is
  process-wide, installed on the first register, and guards its `static`
  list with a mutex.
- `authorizer.rs` — the one authorizer callback, holding the caller's
  deny-list plus the busy slot's own two rules; `query.rs` — the four `core_*`
  entry points and the two input checks that reject bad SQL; `util.rs` —
  term to `rusqlite::Value` conversion both ways, row encoding,
  identifier quoting, `singular_ok_or_error_tuple`;
  `error.rs` and `constraint_parse.rs` —
  `XqliteError` (71 variants) with `classify_sqlite_error`, and the
  constraint message-text parser.
- `schema.rs`, `explain_analyze.rs`, `pragma.rs`, `transaction.rs` — the
  schema structs, their PRAGMA readers and the column-default
  classifier; the scanstatus and plan collector; PRAGMA name validation;
  the transaction and savepoint SQL, names quoted.

## 2. Data flows

### 2.1 A query

`xqlite.ex:query/4` → a `[:xqlite, :query]` span →
`validate_cancel_tokens/1`, then `TypeExtension.encode_params/2`, either
refusal ending the call inside the span →
`nif.rs:query_with_changes_cancellable` (dirty I/O), handed the
`:cancel_tokens` list, `[]` by default, which registers no cancel check →
`connection.rs:with_conn`, which locks the `Mutex` and proves the inner
`Option<Connection>` is `Some`, else `ConnectionClosed` →
`query.rs:core_query_with_changes`, which brackets `core_query` with two
`conn.total_changes()` reads. `core_query` compiles one statement through
`statement.rs:prepare_one`, then binds: an empty list binds
nothing, a keyword list goes through
`util.rs:decode_exec_keyword_params`, which refuses a statement of more
than `MAX_NAMED_PARAMETERS` (2 048) parameters before it reads a value
(each atom key gains a leading `:`),
any other list through `decode_plain_list_params`, `nil` means none,
anything else is `ExpectedList`. Both hand each value to
`util.rs:elixir_term_to_rusqlite_value`, where a binary becomes `Text`
when its bytes are valid UTF-8 and `Blob` otherwise, and a map that is an
`%Xqlite.Blob{}` becomes `Blob` whatever its bytes are — any other map,
and `bytes` holding anything but a binary, is refused.
`util.rs:process_rows` encodes each
value with `encode_val` → `encode_f64` / `encode_text` / `encode_blob`.
`nif.rs:encode_query_result_with_changes` builds the map, the Mutex
releases, and `query/4`'s `decode_result_rows/2` decodes the rows and
builds `%Xqlite.Result{}`; a value an extension refuses ends the call
there with `{:error, _}`, after the statement ran. `execute/4` is the same
path through `nif.rs:execute_cancellable` and `core_execute`, with the
affected count in `Result.changes` and no rows.

### 2.2 Prepared statements

`nif.rs:stmt_prepare` calls `sqlite3_prepare_v2` under `with_conn`,
routing failures through `error.rs:prepare_failure` and snapshotting
column names into the resource. Every later call goes through
`statement.rs:with_live_stmt`, which locks the connection *before*
loading the `AtomicPtr` — that order makes a concurrent finalize safe,
because the finalizer can null the pointer at any moment but cannot call
`sqlite3_finalize` without the same Mutex. Stepping goes through
`stream.rs:process_single_step`, which reads the column count *after* the
step so automatic re-prepare is reflected. `stmt_finalize` and `Drop`
both call `stream.rs:take_and_finalize_raw`: take the connection lock,
swap the shared pointer cell to null, finalize, drop the connection's
registry entry, discard the return code.

### 2.3 Streams

`xqlite.ex:stream/4` → `stream_resource_callbacks.ex:start_fun/1`
(validate `:on_error`, `:batch_size` and `:cancel_tokens`, then
`open_stream/5`: `nif.rs:stream_open`, `stream_get_columns`, and a refusal
of a column list holding a repeated name with
`{:duplicate_column_name, name}` — those last two close the handle they were
handed, while the three option checks run before any handle exists) →
`claim/1` → `next_fun/1` → `nif.rs:stream_fetch_cancellable`, which locks the
connection once and steps up to `batch_size` rows in a single hold, growing
the row vector on demand because pre-sizing to an unvalidated `batch_size`
could abort the VM. On exhaustion or error it swaps the pointer to null and finalizes
there and then, replying `:done` or `{:error, reason}` — except that an
error other than a cancellation, after rows were already read, hands those
rows back now and keeps the error for the next fetch. `fetch_batch/1` hands
each batch to `map_rows_to_maps/4`, which decodes each row through
`TypeExtension.decode_row_checked/2` and keys it by column name, and shapes
each element per `:on_error`. A row holding a value an extension refuses
stops the batch there: the rows before it go out, and the refusal waits in
the accumulator's `decode_error` until the next pull answers it per
`:on_error`, as the NIF does with a step error. `after_fun/1` calls the idempotent
`stream_close`. `stream_open` compiles through
`statement.rs:prepare_one`, so SQL holding no statement and SQL holding a
second one are refused at open rather than becoming an empty stream or a
stream over the first statement alone. `build_acc/5` keeps the connection
and the wrapped `:cancel_tokens` in the accumulator, so every fetch
carries the same token list; an empty list makes the cancellable fetch
byte-for-byte the plain one. `claim/1` is the resource's start function, so
it runs at every enumeration: the first takes the stream with a
compare-and-swap on the accumulator's `claim` cell, and every later one —
after the first or while it still runs — gets a pass with no handle and an
outcome cell of its own, which answers `:stream_consumed` through
`:on_error` and fetches, closes and emits nothing. One exception: a later
pass halted before its first element, in the process where the first pass
runs (`Stream.zip/2` cleaning up after a raise, `Stream.zip([], stream)`),
closes the first pass in its `after_fun/1`, and the first pass's next fetch
then answers `:stream_consumed`.

### 2.4 Hooks and callbacks

A per-connection master callback is installed exactly once, in
`connection.rs:handle_open_result`, and stays for the connection's life;
`register_*` / `unregister_*` only mutate a `hook_util.rs:HookList<T>`,
which is copy-on-write — writers clone the `Vec` and atomic-swap under
the connection Mutex, the C callback reads one atomic load. The commit
and rollback hooks use rusqlite's safe closure API, and the commit
closure always returns `false`, never vetoing. `progress_dispatch.rs`,
`busy_handler.rs`, `wal_hook.rs`, `update_hook.rs` and `authorizer.rs`
register raw `sqlite3_*` callbacks, since rusqlite's wrappers cannot carry
the state they need and its authorizer and update-hook wrappers panic on a
name that is not UTF-8; those that take a name read it as bytes
(`hook_util.rs:c_bytes`). All five run inside
`hook_util.rs:guard_ffi_callback`, so a panic returns a fixed value instead
of unwinding into C: `SQLITE_OK` for the WAL hook, `SQLITE_DENY` for the
authorizer, which then denies the statement it was judging, and 0 for the
other three. Each callback sends with `enif_send` on a
fresh `msg_env`, frees it unconditionally, and rebuilds atoms there.
`log_hook.rs` is process-wide (`sqlite3_config`), so no connection Mutex
is held when it fires; its `static MASTER_LOCK` is taken by the callback
as well as by register/unregister, or the lock-free read would race the
free of the old subscriber vector.

### 2.5 Cancellation

`nif.rs:create_cancel_token` returns a resource holding an
`Arc<AtomicBool>`; `cancel_operation` stores `true` and nothing resets
it. A `*_cancellable` NIF reads its tokens with `cancel.rs:decode_tokens`;
a call whose statement has not started — a one-shot call, a multi-step on
a statement not mid-run, a stream's first fetch, a backup before its first
step — first asks `cancel.rs:cancel_if_signalled`, so an already signalled
token answers `{:error, :operation_cancelled}` before anything runs. Then
it builds a `cancel.rs:ProgressHandlerGuard` inside the `with_conn`
closure — one `CancelSubscriber` per token onto `progress_dispatch.cancels`,
each owning `Arc` held so the raw `*const AtomicBool` stays valid while
reachable — and the guard stores in `busy_before` how many of the
connection's statements are mid-run, the one the call steps left out. The
progress C callback, installed at open time with `PROGRESS_NUM_OPS` = 8,
runs where `cancel-check-every-8-vm-ops` says: at certain jumps and at the
end of every step once 8 VM instructions have run since the last call,
and while SQLite compiles. It walks `cancels` first and returns 1 only when
a flag is set and more statements are mid-run than `busy_before` counted,
that is, while the call's own statement runs: SQLite also calls it after a
statement's last step, past its commit, and while it compiles, where a 1
would cancel a finished write or a compile. SQLite then aborts with
`SQLITE_INTERRUPT`, which `error.rs:classify_sqlite_error` maps to
`{:error, :operation_cancelled}`. Dropping the guard unregisters before
releasing the `Arc`s. Tick subscribers share the callback, each with its
own counter.

`nif.rs:stream_fetch_impl` is the one that does not use `with_conn`: it
declares the guard after its own connection lock guard and after the
connection is proved open, so reverse declaration order drops the guard
while the Mutex is still held. A cancelled fetch goes through the same
`Err` arm as any other fetch error — swap the pointer, finalize, return —
so the stream is closed and `next_fun/1` emits
`[:xqlite, :cancel, :honored]` with `operation: :stream_fetch` before
routing `{:error, :operation_cancelled}` through the `:on_error` mode.

### 2.6 The remaining flows

The busy slot, the WAL slot, error classification and the telemetry gate
are stated in full as facts in section 4. Every C function that takes a
schema name first judges it with `schema.rs:require_schema` in the same lock
hold. `Xqlite.Pragma` judges its `:db_name` in a call of its own
(`XqliteNIF.txn_state/2`) before the call that runs the PRAGMA, so a `DETACH`
between the two answers SQLite's own error (`names-are-judged-before-the-c-call`).
`backup.rs` holds the one step loop `backup`, `backup_with_progress` and
`restore` share, run under the connection lock: no sleep and no retry, a
busy wait of 0 on the connection it opens itself (backup's destination,
restore's read-only source), the cancel tokens read before the destination
is opened and between steps. `serialize` copies the image into an
`OwnedBinary`;
`deserialize` needs `with_conn_mut`. A session is a `Session<'static>`
produced by transmuting away the connection borrow, kept sound by the
`ResourceArc<XqliteConn>` the resource also holds, and every
`sqlite3session_*` call takes the connection Mutex first, the per-session
Mutex second. Two facts live only here: `span_with_stop_metadata` treats
its block's last element as **stop metadata**, so `:stop` measurements
are always just `%{duration, monotonic_time}` and every extra a call
records arrives in the metadata map; and `Xqlite.Telemetry.run_span/3`
emits the three span events itself instead of calling
`:telemetry.span/3`, whose measurements are in the VM's native time
unit while every xqlite measurement is a nanosecond count.

## 3. State machines

### Connection (`connection.rs`)

| State | Event | Next | Function |
|---|---|---|---|
| — | any `open*` NIF | open | `handle_open_result` |
| open | any NIF | open | `with_conn` / `with_conn_mut` |
| open | `close` | closed | `close_connection`: drain the child registry, then `free_handle` closes through `Connection::close()`; a refused close puts the connection back |
| closed | `close` | closed | `close_connection` → `:ok \| {:error, {:database_busy_or_locked, _, _}} \| {:error, {:lock_error, _}}` |
| closed | anything else | closed | `{:error, :connection_closed}` |

`XqliteConn.children` holds one shared pointer cell per prepared
statement, stream and blob xqlite opened on the connection.
`close_connection` finalizes them all under the connection `Mutex` before
dropping the `Connection`, so `sqlite3_close` frees the handle instead of
answering `SQLITE_BUSY`. Statements a virtual-table module owns are not in
the registry — SQLite disconnects those itself during close. A session
registers nothing and is still leaked by an explicit close.

### Prepared statement (`statement.rs`)

A second flag rides alongside the live/final one: whether anything has set
the statement's parameters. It starts false for a statement that takes one or
more and true for one that takes none, and only a step reads it. A third
piece of state is not the library's: SQLite's own `sqlite3_stmt_busy`, which
`stmt_bind` and `stmt_clear_bindings` read to refuse a bind or a clear in the
middle of a run.

| State | Event | Next | Function |
|---|---|---|---|
| — | `stmt_prepare` | live, parameters unset (set when the statement takes none) | `nif.rs:stmt_prepare` reads `sqlite3_bind_parameter_count` beside the column count |
| live, parameters unset | a step of any kind | unchanged | `{:error, {:parameters_unbound, %{expected: n}}}`, behind the liveness check |
| live | a bind that succeeded | live, parameters set | `nif.rs:stmt_bind` |
| live | a bind the library refused (the count, the names, a value it cannot convert, a value over the connection's length limit) | unchanged | the whole list is judged before the first bind, so nothing was bound and an earlier successful bind stays in force |
| live | a bind SQLite refused after it had taken values | live, parameters unset | the values before the failing one stayed bound and that one is NULL, which is no state to run: `nif.rs:stmt_bind` clears the flag inside the same lock. The length check before the bind loop leaves an allocation failure as the only way here |
| live | `stmt_clear_bindings` | live, parameters set | every parameter is NULL on purpose |
| live, mid-run, the statement takes parameters | `stmt_clear_bindings` | unchanged | `{:error, :statement_mid_run}`: `sqlite3_clear_bindings` has no mid-run check of its own, so the clear would release the values in place and leave every row still to come reading NULL. `sqlite3_stmt_busy`, read under the same lock as the clear, is the tell: non-zero while the statement is mid-run — a step answered a row, or was refused as busy while taking or committing its lock (SQLite keeps that run for a retry), and neither `SQLITE_DONE`, another failure nor a reset followed. A statement that takes no parameters has nothing to release and is cleared as anywhere else |
| live, mid-run, the statement takes parameters | `stmt_bind` | unchanged | `{:error, :statement_mid_run}`, from the same tell read first under the bind's lock, before the list is walked; SQLite itself would refuse the bind with a misuse. A statement that takes none binds `[]` mid-run as `:ok` |
| live, the run over (`:done` or a failed step) | `stmt_bind` | live, parameters set | `nif.rs:stmt_bind` resets the statement under the same lock, then binds, so the next step reruns with the new values: SQLite refuses a bind there with a misuse, though its own next step would reset the statement unasked |
| live | `stmt_reset` | unchanged | SQLite keeps the bindings across a reset |
| live | bind / reset / clear | live | `with_live_stmt` |
| live | `stmt_step` → `{:row, _}` | live | `process_single_step` |
| live | `stmt_step` → `:done` | live | auto-resets on next step |
| live | a step reads a row it cannot decode, after other rows of the batch | live, error held | `stmt_multi_step_impl` hands back the rows with `done: false` and keeps the error in `XqliteStatement.pending_error` |
| live, error held | `stmt_step`, `stmt_multi_step` or its cancellable twin | live | answer the held error and empty the slot, before stepping; the statement carries on at the row after the bad one |
| live, error held | `stmt_reset` | live | empty the slot: the run it belonged to is over |
| live, error held | `stmt_finalize` | final | empty the slot and answer the lifecycle result |
| live | a step that fails outright (busy, I/O, a runtime error in the SQL, a trigger's `RAISE`, a cancellation) | live | `StepFailure::Failed`: answer at once, discard the batch's rows, hold nothing; the run is over and SQLite reruns from the top on the next step — except after a step refused as busy while taking or committing its lock, which SQLite keeps mid-run so the next step retries it |
| live | `stmt_finalize` or GC | final | `take_and_finalize_raw` |
| live | the connection is closed | final | `close_connection` drains the registry |
| final | any step or bind | final | `{:error, :statement_finalized}` |
| final | `stmt_column_names` | final | prepare-time snapshot |
| final | `stmt_finalize` | final | `:ok` |

### Stream (`stream.rs`, `stream_resource_callbacks.ex`)

| State | Event | Next | Function |
|---|---|---|---|
| — | `stream_open` | open | `nif.rs:stream_open` |
| — | `stream_open` with no statement, or with a second one | — | refused by `statement.rs:prepare_one`, no handle |
| open | `stream_fetch` → rows | open | `nif.rs:stream_fetch` |
| open | `stream_fetch` exhausts | closed | swap + finalize in place |
| open | `stream_fetch` errors with no row of that batch read | closed | swap + finalize, then error |
| open | `stream_fetch` errors after reading rows | closed, error held | swap + finalize, hand back the rows, keep the error in `XqliteStream.pending_error`; both failure kinds are held back here, the statement being finalized already |
| closed, error held | `stream_fetch` | closed | answer the held error and empty the slot, before any step |
| open | `stream_fetch_cancellable` with a signalled token | closed | swap + finalize, discard the batch's rows, then `{:error, :operation_cancelled}` |
| any | `stream_close` or GC | closed | `take_and_finalize_atomic_stmt`, which empties the held error first |
| open | the connection is closed | closed | `close_connection` drains the registry |
| closed | `stream_fetch` | closed | `:done` |
| claimed | another enumeration of the `stream/4` Enumerable | unchanged | `claim/1` finds the claim taken: a pass with no handle answers `:stream_consumed` through `:on_error`, with no fetch, no close and no telemetry event |
| claimed | that later pass halted before its first element, in the first pass's process | closed | `after_fun/1` closes the first pass through `close_once/1` (close event `:halted`); the first pass's next fetch answers `:stream_consumed` through `:on_error` |

`stream_fetch` proves the connection open before it reads the statement
pointer: after a close both are gone, and the caller must still hear
`{:error, :connection_closed}` rather than `:done`. It then looks for a
held error, before the batch loop — a finalized statement's null pointer
would otherwise answer `:done` and the stream would look complete.

The busy slot's own transitions are in section 4
(`busy-slot-policy-single-observers-many` and
`busy-slot-restores-displaced-timeout`): the slot moves between empty,
policy, observers and both, restoring the displaced `busy_timeout` on
every transition into empty and recording the current one on the way out.
Both edges also re-install the connection's authorizer, since the held
slot adds rules of its own; a take that then fails puts the flag back and
re-installs again.

Blobs share the stream's two-state shape, closing on the connection's
close as well; a session does not, and an explicit close leaks it. A poisoned
`Mutex` is terminal everywhere: `{:error, {:lock_error, _}}`.
`nif.rs:txn_state` maps `sqlite3_txn_state` (a NULL name for `:all`) to
`:none`, `:read`, `:write`, or `:unknown`. `nif.rs:autocommit` reads
`sqlite3_get_autocommit` instead, and `nif.rs:transaction_status`, which
only the raw `XqliteNIF.transaction_status/1` exposes, reads its negation:
after `BEGIN DEFERRED`, before any statement runs, autocommit is off while
`txn_state` still answers `:none`.

## 4. Shared facts with consumers

Facts more than one place in the tree relies on. For every row, the full
consumer list and the `rg` / `ast-grep` patterns that regenerate it live
in the review registry, in the workdir that `AGENTS.md` names. Paths
below are relative: Elixir to `lib/`, Rust to `native/xqlitenif/src/`,
pins to `test/`.

| id | statement | producer | pin |
|---|---|---|---|
| `changes-reported-on-total-delta` | query_with_changes and the three execute functions report sqlite3_changes() only when sqlite3_total_changes() moved across the statement, and 0 otherwise (query.rs:changes_since, shared by core_query_with_changes and core_execute); sqlite3_changes() itself is sticky and survives SELECT, DDL and PRAGMA. Two kinds of DDL report a count: a DROP TABLE that SQLite precedes with a DELETE (of a table a foreign key references, or of a table with a deferred foreign key of its own while a deferred violation is pending), with foreign_keys on, reports the rows of that implicit DELETE, as sqlite3_changes() does; and CREATE VIRTUAL TABLE with a module that writes rows into tables of its own while it creates them (rtree, fts5) reports 1, the module's own INSERT, where fts4 and a plain CREATE report 0. | `query.rs:core_query_with_changes`, `query.rs:core_execute`, `query.rs:changes_since` | `nif/query_with_changes_test.exs: "DDL after DML returns changes 0 (no sticky leak)", "the execute functions count only the rows the statement changed"; nif/execution_test.exs: "every execute function runs a RETURNING write to its end and answers its count"` |
| `conn-mutex-covers-every-sqlite-call` | Every sqlite3_* C call on a connection another thread can reach runs with the connection Mutex held for its whole duration (a connection no other thread can reach takes no lock: backup's destination and restore's source, both opened by backup.rs:open_file, and judge_image's scratch connection, each opened and dropped inside one call, and the new connection keep_read_only checks before the open returns it); an AtomicPtr swap gives pointer ownership, never connection access. The cancel-token guard a fetch registers is dropped before the connection lock is released, because the hook list frees the old subscriber vector right after its atomic swap while the C progress callback reads that vector without a lock. A Rust copy of a SQLite setting (the extension switch) is written and read in the same lock hold as the C call it decides. | `connection.rs:with_conn` | `nif/cancellation_test.exs: "a reader on the same connection waits while a statement runs on it"` |
| `cancel-check-every-8-vm-ops` | SQLite calls the progress handler at certain jumps (a loop's bottom, a trigger's entry, the Goto that ends a statement's setup) and at the end of every step, once at least 8 VM instructions (PROGRESS_NUM_OPS in progress_dispatch.rs) have run since the last call, counting across runs of the same prepared statement, and at intervals while it compiles a statement; a one-row write without a loop or a trigger, run once, is first checked after its end. That bounds cancellation latency for a statement that loops and sets the unit a progress hook's every_n counts. | `progress_dispatch.rs:PROGRESS_NUM_OPS` | `nif/stream_cancel_test.exs: "a table scan reports the cancel within three single-row fetches"` |

## 5. Build facts

- **SQLite compile flags.** `native/xqlitenif/.cargo/config.toml` sets
  `LIBSQLITE3_FLAGS = "-DSQLITE_ENABLE_STMT_SCANSTATUS=1"`, without which
  `sqlite3_stmt_scanstatus_v2` returns `SQLITE_MISUSE` and
  `Xqlite.explain_analyze/3` has nothing to report. Everything else comes
  from `libsqlite3-sys`'s bundled build, which always passes
  `-DSQLITE_ENABLE_API_ARMOR`, `-DSQLITE_THREADSAFE=1`,
  `-DSQLITE_DEFAULT_FOREIGN_KEYS=1`, `-DSQLITE_ENABLE_FTS5`,
  `-DSQLITE_ENABLE_RTREE`, `-DSQLITE_ENABLE_STAT4`,
  `-DSQLITE_ENABLE_COLUMN_METADATA`, `-DSQLITE_ENABLE_DBSTAT_VTAB` and
  more; the `session` cargo feature adds `-DSQLITE_ENABLE_SESSION` and
  `-DSQLITE_ENABLE_PREUPDATE_HOOK`. Nothing here can turn API_ARMOR off.
- **Cargo must run from the crate directory,** because it finds
  `.cargo/config.toml` only by walking up from its working directory;
  `--manifest-path` from the repo root loses `LIBSQLITE3_FLAGS`, so
  `lib/mix/tasks/verify.ex:run_cargo/1` sets `cd: "native/xqlitenif"`.
- **Threading.** `SQLITE_THREADSAFE=1` is the compiled mode, but rusqlite
  opens every connection with `SQLITE_OPEN_NO_MUTEX`, so the Rust
  `Mutex<Connection>` is the only serialization. The two are
  complementary: `rusqlite::Connection` is `!Sync`, so the Rust `Mutex`
  is required by the type system anyway, and NO_MUTEX is safe *because*
  it is there. `open_readonly` and `open_in_memory_readonly` pass
  NO_MUTEX explicitly; the rest inherit it from `OpenFlags::default()`.
- **Rustler and NIF versions.** `Cargo.toml` declares the cargo features
  `nif_version_2_15` / `2_16` / `2_17`, defaulting to `2_17`, and sets
  `lto = true` with `codegen-units = 1` for release builds; the Rust
  edition and toolchain floor live there too.
  `lib/xqlite/xqlitenif.ex` declares `nif_versions: ["2.17"]` and the
  eight precompiled targets, and drives `force_build:` off the
  `XQLITE_BUILD` environment variable.
- **Telemetry flag.** `lib/xqlite/telemetry.ex` reads
  `Application.compile_env(:xqlite, :telemetry_enabled, false)` — a
  compile-time value, so changing it needs
  `mix deps.compile xqlite --force`. **Warnings as errors:** `mix.exs`
  sets `elixirc_options: [warnings_as_errors: true]` for `lib/`, and the
  `test:` alias appends `--warnings-as-errors`, which `mix test.seq`
  inherits when it shells out to `mix test` per file.
